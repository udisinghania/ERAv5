# ERA V5 Session 6 - Training Data Execution System

This repository implements the complete Session 6 path:

```text
documents -> tokenized shards -> manifests -> mixture schedule -> packing
-> batches -> training -> consumption ledger -> learning ledger -> checkpoint
-> crash -> resume -> replay -> fork -> audit
```

The goal is correctness, reproducibility, auditability, and measured efficiency
on a laptop-scale model. Model quality at production scale is intentionally out
of scope.

## Architecture overview

The implementation is organized as a sequence of independently verifiable
contracts:

1. Source snapshots are cleaned, decontaminated, permissioned, and frozen.
2. A content-hashed tokenizer creates immutable token and loss-mask shards with
   manifests linking every shard to its source and tokenizer.
3. The curriculum compiler converts lane weights, protected floors, Indic tiers,
   and annealing reserves into exact integer loss-token quotas.
4. The packer creates fixed-length sequences with document-isolated segment IDs,
   reset position IDs, padding masks, and origin-aware loss masks.
5. OPUS converts packed sequences into deterministic microbatches while recording
   accepted, rejected, deferred, and protected-floor-override proposals.
6. The Transformer consumes those microbatches and writes cross-linked,
   hash-chained consumption and learning ledgers with per-sequence losses.
7. Checkpoints bind model, optimizer, RNG, next-batch proof, and ledger offsets.
8. The recovery controller deliberately crashes, resumes, replays a historical
   interval, creates a fork, and independently audits all reconstructed hashes.

`run_demo.py` is the top-level orchestrator. Implementation code lives under
`src/`, executable stages under `scripts/`, frozen policies under `configs/`,
automated invariants under `tests/`, and final evaluator-facing evidence under
`submission_artifacts/`.

## Design decisions

- Loss-bearing tokens, rather than characters or physical padded tokens, are the
  accounting unit for curriculum quotas, training consumption, and throughput.
- Content hashes and canonical JSON make tokenizer, manifests, batch plans,
  ledgers, and evidence independently reconstructable rather than trusting file
  names or mutable metadata.
- Validation and never-train records are blocked before scheduling and checked
  again at later gates; validation probes never contribute gradients.
- Packed documents use separate segment IDs and reset positions so packing
  improves utilization without creating cross-document attention.
- OPUS rejection applies to a candidate proposal, not permanent deletion of its
  underlying samples; protected floors remain hard constraints.
- Checkpoints are committed only at optimizer boundaries and contain the exact
  next-batch reconstruction proof plus ledger tails, preventing skip/repeat on
  resume.
- Replay preserves the historical stream exactly, whereas a fork records its
  parent checkpoint and declared policy change before intentional divergence.
- CPU and CUDA are supported as separate deterministic backends. Exact replay is
  required within one backend, not across different floating-point kernels.

## Completion proof: consumed, selected, learned, reconstructed

The assignment is considered complete only if the generated system can answer
four questions with reproducible evidence. This implementation answers them as
follows; the files below are regenerated by `python run_demo.py`, not manually
authored PASS claims.

| Required question | What the system proves | Generated evidence |
|---|---|---|
| **What did it consume?** | The hash-chained consumption ledger records every microbatch in order, including batch index, curriculum stage, sequence IDs, physical and loss-bearing token counts, exact token spans, payload hashes, and the batch reconstruction proof. Each packed sequence is consumed exactly once. | `submission_artifacts/ledgers/baseline_consumption.jsonl.gz`, `submission_artifacts/manifests/batches.jsonl.gz`, `submission_artifacts/manifests/training_report.json` |
| **Why did it consume it?** | The frozen schedule explains the stage and lane quota for every loss-bearing token. The OPUS decision ledger records all candidate scores and the accepted, rejected, or deferred outcome, including protected-floor overrides for Indic and agentic data. The evaluation firewall proves never-train data was ineligible. | `submission_artifacts/manifests/schedule.json`, `submission_artifacts/manifests/opus_decisions.jsonl.gz`, `submission_artifacts/manifests/batch_report.json`, `submission_artifacts/manifests/freeze_report.json` |
| **What did the model learn from it?** | Every learning event is cross-linked to its consumption entry and records shifted masked cross-entropy, loss-bearing token count, per-sequence loss, optimizer-update diagnostics, learning rate, gradient norm, and parameter hash after updates. The validation probe is permission-isolated and never contributes gradients. | `submission_artifacts/ledgers/baseline_learning.jsonl.gz`, `submission_artifacts/ledgers/baseline_consumption.jsonl.gz`, `submission_artifacts/manifests/training_report.json` |
| **How can the run be reconstructed?** | The checkpoint binds model, optimizer, RNG state, batch cursor, ledger tails, and the expected next-batch proof. The deliberate crash resumes at the exact expected batch without skip or repetition. Historical replay rechecks batch IDs, sequence IDs, token spans, payload hashes, proof hashes, ledgers, and final parameters. The fork preserves its parent lineage and diverges only after the declared policy change. | `submission_artifacts/checkpoints/`, `submission_artifacts/manifests/crash_event.json`, `submission_artifacts/manifests/resume_event.json`, `submission_artifacts/manifests/replay_interval_report.json`, `submission_artifacts/manifests/recovery_audit.json` |

The proof chain is anchored by immutable corpus, tokenizer, schedule, packing,
batch-plan, training, checkpoint, and recovery-audit hashes in
`submission_artifacts/evidence.json`. `submission_artifacts/evidence.md` provides
the human-readable requirement table, while
`python scripts/verify_submission_bundle.py` independently rehashes and
cross-checks the generated bundle.

## Runtime target

- Any CUDA device supported by the pinned PyTorch build is preferred
- A deterministic CPU fallback is supported for evaluators without CUDA
- The measured reference run uses an NVIDIA RTX 3070 laptop GPU
- Tiny decoder-only Transformer
- 256- and 512-token curriculum contexts

GPU and CPU runs are each internally deterministic, resumable and replayable.
Exact parameter equality is required within one selected backend; floating-point
results are not claimed to be byte-identical across CPU and CUDA implementations.

### Expected runtime

Runtime depends on CPU/GPU speed and filesystem performance. The latest submitted
CPU reference measured the primary 262,144-loss-token training loop at 22.97
seconds and 11,411 useful loss-bearing tokens/second. The complete command also
regenerates data artifacts and executes crash/resume, replay, and fork workers;
allow approximately 2-5 minutes on a modern laptop CPU. A compatible CUDA GPU is
normally faster. The generated `submission_artifacts/performance.json` records
the actual synchronized training duration and reconstructable token rates for
each submitted run.

## Executable data lanes

The Session 5 recipe is represented by seven primary lanes:

1. General web
2. Science and mathematics
3. Code
4. Explicit reasoning
5. Long context
6. Indic, split into verified, unverified, translated, and synthetic tiers
7. Agentic trajectories

Evaluation, validation, and annealing data are permissions/reserves, not extra
primary lanes. A record receives one primary lane so token supply cannot be
double counted.

## Fresh-checkout setup

Create an environment with either the GPU or CPU dependency contract:

```powershell
py -3.12 -m venv .venv
# CUDA 12.1 build:
.\.venv\Scripts\python.exe -m pip install -r requirements-gpu.txt
# Or CPU-only build:
.\.venv\Scripts\python.exe -m pip install -r requirements-cpu.txt
```

The complete submission command, using whichever Python interpreter launches
it, is:

```bash
python run_demo.py
```

`--device auto` is the default. It prefers CUDA and falls back to CPU. Explicit
execution is also available:

```bash
python run_demo.py --device cuda
python run_demo.py --device cpu
```

It regenerates `submission_artifacts/` without network access. The command
freezes the reviewed documents, retrains the frozen tokenizer, rewrites and
validates all shard manifests, compiles the mixture, packs and batches the
schedule, executes training on the selected device, measures throughput, deliberately crashes a
separate worker, resumes at the proven next batch, replays a historical
interval, creates a checkpoint fork, audits every comparison, and generates
the required evidence bundle without manual intervention.

The generated structure is:

```text
submission_artifacts/
  run.log
  evidence.json
  evidence.md
  manifests/
  ledgers/
  checkpoints/
  performance.json
```

Artifact roles:

- `run.log` records the ordered execution trace and all required PASS events.
- `evidence.json` maps each graded requirement to machine-readable supporting
  paths and hashes; `evidence.md` is the corresponding human-readable table.
- `manifests/` contains frozen tokenizer, shard, schedule, batch, training, and
  audit metadata needed to reconstruct claims.
- `ledgers/` contains OPUS decisions plus hash-chained consumption and learning
  histories, including replay and fork comparisons.
- `checkpoints/` contains the crash boundary, resumed result, clean replay, fork,
  and final model states tied to ledger offsets.
- `performance.json` reports physical, nonpadding, and useful loss-bearing token
  rates together with packing utilization and the precise timing scope.

## Deterministic microbatches and auditable OPUS

The packed sequences are arranged into fixed 1,024-physical-token
microbatches. At each decision, metadata-proxy OPUS compares up to four
deterministic candidate proposals, applies an explicit acceptance gate, defers
valid unselected proposals, and can override the raw proxy winner to repair
protected-lane pacing while preserving exact schedule totals:

```bash
python scripts/build_batches_v1.py
python scripts/verify_batches_v1.py
```

Read `docs/BATCHING_AND_OPUS_REPORT.md` for microbatch shapes, proposal
acceptance/rejection/deferral, protected-floor overrides, proxy scoring, the
complete decision ledger, zero-loss context handling, and reconstruction proof.

## Crash recovery, replay, and fork

The recovery demonstration checkpoints every eight optimizer updates,
deliberately exits after update 32, resumes in a new process, performs an exact
clean replay, and creates a lineage-tracked half-learning-rate fork:

```powershell
$env:ERA6_DEVICE = "auto"  # keep the same selection across the recovery protocol
python scripts\run_recovery_demo_v1.py
python scripts\verify_recovery_v1.py
```

Read `docs/RECOVERY_REPLAY_FORK_AUDIT.md` for checkpoint contents, crash
semantics, exact ledger comparisons, the fork boundary, and the independent
